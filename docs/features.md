## 0. MVP의 목적

**QR로 들어온 방문자가 도슨트를 듣고 → 스마트스토어로 가거나 → 체험을 예약하는지**를 방문(세션) 단위로 끝까지 추적하는 것이 이 MVP의 핵심이다.
따라서 **행동 데이터 수집(§2)과 예약(§3)이 1순위**다. 나머지 화면은 이 흐름을 받쳐 주는 역할이다.

## 2. 행동 데이터 (세션 추적)

### 2-1. 방식

- 방문자가 사이트에 들어오면 **익명 세션 ID(UUID)** 를 만들어 브라우저에 저장한다. 이름·연락처 같은 개인정보는 여기에 들어가지 않는다.
  - 30분 동안 아무 행동이 없으면 새 세션으로 본다(GA와 같은 기준).
  - 같은 기기에서 다시 방문했는지 보려고 `visitor_id`를 별도로 오래 저장한다(재방문 분석용).
- 모든 이벤트는 우리 DB(Supabase `events`)에 직접 저장한다. **GA4는 보조로 쓰고, 원본 데이터는 우리 DB에 둔다.**
- 페이지를 닫거나 앱을 전환해도 마지막 이벤트가 유실되지 않도록 `navigator.sendBeacon`으로 보낸다.
- 전송 경로는 `/api/track`(Route Handler)이다. 서버에서 형식을 검사하고 rate limit을 건 뒤 service role로 insert한다. 클라이언트가 DB에 직접 쓰지 않게 한다.

### 2-2. 수집 이벤트

| 이벤트 | 언제 | 주요 값 | 답하려는 질문 |
|---|---|---|---|
| `session_start` | 세션 시작 | 진입 경로(QR 코드 / utm / 직접), 첫 페이지, 언어, 기기(OS·브라우저), 리퍼러 | 어디서 들어오나 |
| `page_view` | 페이지 이동 | 경로, 장인/공예 ID | 무엇을 보나 |
| `docent_play` | 재생 시작·재개 | 장인, 트랙, 언어, 시작 위치 | 듣기 시작하나 |
| `docent_pause` | 일시정지 | 멈춘 위치(초), 누적 청취 시간 | **듣다 끊는가, 어디서** |
| `docent_progress` | 25·50·75% 도달 | 진행률 | 얼마나 듣나 |

### 2-3. 데이터로 답할 수 있는 것

- 방문 → 도슨트 재생 → 완청 → 스토어 클릭 / 예약 완료, 각 단계의 **세션 전환율**
- 장인별·QR 위치별·언어별 비교
- 도슨트 **이탈 구간 분포**(어느 지점에서 많이 끊는지). 원고·편집 개선에 쓴다.
- "도슨트를 들은 사람"과 "안 들은 사람"의 예약·스토어 전환율 차이. **MVP 핵심 검증 지표**다.

### 2-4. 한계 (사전 공유)

- **스마트스토어 구매 여부는 우리 쪽에서 알 수 없다.** 우리가 확인할 수 있는 건 "스토어로 넘어갔다"까지다.
  → 스토어 링크에 네이버 유입 추적 파라미터(`nt_source=aoull&nt_medium=qr&nt_detail={장인}` 등)를 붙인다. 그러면 **스마트스토어 통계에서 우리 유입분의 구매**를 따로 볼 수 있다. 정확한 파라미터 규칙은 스토어 연결 시점에 확인한다.
- 같은 사람이 폰을 바꾸거나 브라우저 데이터를 지우면 다른 방문자로 집계된다.

## 3. 캘린더 예약

### 3-1. 흐름

1. 장인 페이지 "체험 예약" → 예약 페이지(해당 장인 미리 선택)
2. **달력**에서 예약 가능한 날짜만 활성화된다(정해진 요일만).
3. 날짜를 고르면 시간 슬롯과 **남은 자리**가 보인다(예: 14:00 · 잔여 3/6).
4. 인원 선택 → 이름·연락처 입력 → 필수 동의 체크 → 신청
5. 완료 화면에 예약 요약과 "체험 전날 확정 연락을 드립니다" 안내를 보여준다.

### 3-2. 운영 규칙 (관리자 설정)

- **일정 규칙**: 장인(또는 공예)별로 요일·시작 시간·정원·소요 시간을 정한다. 예: 매주 토 10:00·14:00, 정원 6명
- **예외**: 특정 날짜 휴무, 특정 날짜 추가 회차, 정원 변경
- **예약 가능 기간**: 예: 오늘 기준 1일 후 ~ 60일 이내(당일 예약은 막음)
- **초과 예약 방지**: 슬롯의 (확정+대기 인원 합계 + 신청 인원) ≤ 정원을 DB 함수 안에서 행 잠금으로 확인한 뒤 저장한다. 동시에 두 명이 마지막 자리를 신청해도 한 명만 성공한다.
- 상태: `대기(신청)` → `확정`(전날 연락 완료) / `취소` / `노쇼`
- 관리자 달력: 날짜별 회차, 인원 합계, 명단, 상태 변경

### 3-3. 받는 정보 (최소 수집)

| 항목 | 필수 | 비고 |
|---|---|---|
| 이름 | ✅ | |
| 연락처(휴대폰) | ✅ | 형식 검증, 확정 연락용 |
| 인원 | ✅ | 슬롯 정원 계산용 (개인정보 아님) |
| 날짜·회차 | ✅ | |
| 요청사항 | 선택 | 자유 입력. 민감정보를 적지 않도록 안내 문구 추가 |

## 4. 개인정보 보호 — 법적 기준 체크리스트

> 근거: 「개인정보 보호법」 제15조(수집·이용), 제21조(파기), 제22조(동의 방법), 제22조의2(아동), 제29조(안전조치), 제30조(처리방침), 「개인정보의 안전성 확보조치 기준」.
> 이 절은 개발 체크리스트다. **법률 자문이 아니다.** 공개 전에 처리방침 문안은 운영 측이 한 번 검토한다.

### 4-1. 예약 폼 동의 (필수 고지 4가지)

수집·이용 동의를 받을 때 아래 4가지를 **다른 문구와 구분해서** 보여주고, 체크박스로 따로 동의를 받는다(미리 체크해 두지 않는다).

| 고지 항목 | 문안(안) |
|---|---|
| 수집 항목 | 이름, 휴대전화번호 |
| 수집·이용 목적 | 체험 예약 접수 및 **체험 전날 참석 확정 연락** |
| 보유·이용 기간 | **체험일로부터 30일 후 파기** (취소 시 취소일로부터 30일) |
| 동의 거부 권리 | 동의를 거부할 수 있으며, 거부 시 체험 예약이 불가합니다 |

- **만 14세 미만**은 법정대리인 동의가 필요하다. MVP에서는 "만 14세 이상입니다" 확인 체크를 추가하고, 14세 미만은 보호자가 대신 신청하도록 안내한다.
- **마케팅 활용은 하지 않는다.** 나중에 하려면 별도 선택 동의를 받아야 한다. 지금은 받지 않는다.
- 예약 정보를 **장인(공방)에게 넘기는 경우** 제3자 제공 동의가 따로 필요하다 → §7 질문 3

### 4-2. 개인정보 처리방침 페이지 (필수)

- `/{locale}/privacy`에 공개하고, 푸터와 예약·문의 폼에서 링크한다.
- 포함 항목: 처리 목적, 항목, 보유 기간, 파기 절차·방법, 제3자 제공·처리위탁(Supabase·Vercel 등 인프라 = **처리위탁 및 국외 이전** 고지 필요), 정보주체 권리 행사 방법, 안전조치, **자동 수집 장치(쿠키·방문기록) 설치·운영 및 거부 방법**, 개인정보 보호책임자 연락처, 시행일
- 방문 행동 데이터는 익명 ID 기반이다. 하지만 예약 시점에 예약 ID와 세션이 연결되므로 "서비스 이용기록"으로 처리방침에 명시한다.

### 4-3. 기술적 안전조치

- [ ] 전 구간 HTTPS (Vercel 기본)
- [ ] 예약·문의 테이블 RLS: 공개 쪽은 **insert만**, 조회는 관리자만. 공개 API로는 남은 자리 수만 노출하고 명단은 절대 노출하지 않는다.
- [ ] 관리자 계정 최소화 + 강한 비밀번호. 가능하면 2단계 인증(Supabase MFA)
- [ ] **관리자 접속·열람 기록 보관**: 누가 언제 예약 명단을 봤는지 `admin_access_logs`에 남기고 1년 이상 보관한다(안전성 확보조치 기준).
- [ ] **자동 파기**: 매일 1회 보유기간이 지난 예약의 이름·연락처를 삭제한다. 통계용 행은 남기고 개인정보 칸만 비운다(Supabase cron 또는 Vercel Cron).
- [ ] 관리자 화면 휴대폰 번호 마스킹 기본(010-****-1234). 연락이 필요할 때만 펼쳐 보고, 펼친 기록을 남긴다.
- [ ] 스팸·대량 신청 방지: honeypot + 요청 제한 + (필요 시) Turnstile

## 5. 관리자 로그인 설계

- Supabase Auth 이메일+비밀번호. **회원가입 화면은 없다.** 계정은 Supabase 대시보드에서 초대로 만든다.
- `admins` 테이블에 등록된 사용자만 `/admin` 접근 가능(서버 레이아웃에서 검사 + RLS `is_admin()`)
- 역할(선택): `owner`(전체) / `editor`(매거진만). MVP는 owner 하나로 시작해도 된다.
- 일반 방문자 로그인은 없다(예약도 비로그인).

## 6. 데이터 모델 변경안 (초기 마이그레이션 대비)

```
visitors            id(uuid) · first_seen_at · last_seen_at · device(os/browser) · first_locale
sessions            id · visitor_id · started_at · last_event_at · entry_type(qr|utm|direct|referral)
                    · qr_code · utm_source/medium/campaign · referrer · landing_path · locale
events              id(bigint) · session_id · type · occurred_at · path · artisan_id · track_id
                    · locale · position_sec · listened_sec · progress_pct · props(jsonb)
experience_rules    id · artisan_id|craft_id · weekday(0-6) · start_time · duration_min
                    · capacity · valid_from · valid_to · is_active
experience_slots    id · rule_id? · artisan_id|craft_id · starts_at · capacity · status(open|closed)
                    (규칙으로 미리 생성 + 예외는 개별 수정)
reservations        (기존 수정) slot_id · party_size · name · phone · status(pending|confirmed|
                    canceled|no_show) · session_id · privacy_agreed_at · age14_confirmed
                    · purge_after(date) · purged_at
admin_access_logs   id · admin_id · action(view_list|reveal_phone|update_status|export) · target · at
posts               (기존) + status(draft|published) · author_id · body(Tiptap JSON, locale별)
```

- 공개용 RPC `get_available_slots(artisan, from, to)` → 날짜·시간·남은 자리 수만 반환한다.
- 예약 RPC `create_reservation(...)` → 정원 확인과 insert를 한 트랜잭션에서 처리한다(초과 예약 방지).
- `events`는 양이 빨리 늘어난다. 월 10만 방문 × 약 15이벤트 ≈ 150만 행/월이다. Supabase Free(500MB) 기준 몇 달은 충분하지만, 오래된 원본은 월별로 집계한 뒤 정리한다.

## 7. 결정 필요 (확인 요청)

1. **체험 요일·시간·정원**: 어떤 요일, 몇 시, 회차당 몇 명? 장인별로 다른가, 공통인가?
2. **1건에 여러 명 예약** 허용? (예: 가족 3명을 한 번에) 허용한다면 최대 몇 명?
3. **예약 명단을 장인(공방)에게 전달하는가?** 전달한다면 제3자 제공 동의 문구가 추가된다. 아울만 연락한다면 필요 없다.
4. **확정 연락 수단**: 전화 / 문자 / 카카오 알림톡? (문자·알림톡을 자동 발송하려면 발송 서비스 연동과 비용이 생긴다)
5. **처리방침 기재 정보**: 운영 주체(상호), 개인정보 보호책임자 이름·연락처
6. **관리자 계정**: 몇 명? 매거진만 쓰는 사람이 따로 있나?

## 8. 구현 순서 (제안)

1. 행동 데이터 수집 파이프라인 (`/api/track`, 세션, 도슨트 이벤트). Supabase가 없어도 먼저 구현하고, 로컬에서는 콘솔·파일로 확인한다.
2. 예약 UI: 달력 → 슬롯 → 인원 → 폼 → 완료. 목업 슬롯으로 먼저 만든다.
3. 개인정보 동의 UI + 처리방침 페이지 (문안 초안)
4. **Supabase 연결** 후 스키마·RPC·RLS 적용, 실제 저장
5. 관리자: 로그인 → 예약 캘린더 → 일정 설정 → 매거진 에디터 → 대시보드
